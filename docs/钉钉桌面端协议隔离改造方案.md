# 钉钉桌面端协议隔离改造方案

**文档状态：** 待开发评审  
**整理日期：** 2026-08-28  
**适用范围：** Multica Web、Electron 桌面端、DingTalk OAuth 服务端  
**目标版本：** `Multica Lechun` 定制桌面版

---

## 1. 背景与问题

目前需要同时使用三个 Multica 版本：

1. 本地开发版；
2. 官方 Multica 桌面版；
3. 基于 Multica 源码打包的个人定制版。

三个版本如果共用 `multica://` 协议，macOS、Windows 或 Linux 可能无法准确判断应由哪个应用接收 OAuth 回调。典型表现包括：

- 定制版登录后跳转到官方 Multica；
- 本地开发版抢占正式版的协议回调；
- 官方版与定制版同时安装时，后安装的应用覆盖协议注册；
- 桌面端收到回调后因协议不匹配而忽略 URL。

因此，定制版需要使用独立的 URL Scheme，并让 OAuth 状态、网页回调、桌面端处理逻辑和打包配置保持一致。

## 2. 改造目标

- 为本地开发版、官方版、定制版分配互不冲突的协议。
- 让 DingTalk OAuth 回调准确回到发起授权的桌面版本。
- 尽量通过独立模块和独立打包配置实现，减少对 Multica 源码主流程的侵入。
- 保持官方桌面版和本地开发版现有行为不变。
- 定制版可以独立安装、调试和发布，不覆盖官方版。
- 不把任何密钥、`.env` 内容或线上环境变量写入仓库。

## 3. 版本与标识约定

| 版本 | 应用名称 | Bundle/App ID | OAuth 客户端标识 | 回调协议 |
| --- | --- | --- | --- | --- |
| 本地开发版 | Multica Canary | `ai.multica.desktop.dev` | `desktop-dev` | `multica-dev://` |
| 官方桌面版 | Multica | `ai.multica.desktop` | `desktop` | `multica://` |
| 个人定制版 | Multica Lechun | `ai.multica.desktop.lechun` | `desktop-lechun` | `multica-lechun://` |

说明：

- `multica-lechun://` 只用于浏览器完成 OAuth 后跳回本机应用。
- 钉钉开放平台仍配置 HTTPS 回调地址，不配置自定义协议。
- Bundle/App ID 与协议都要隔离；只改协议而不改 App ID，仍可能出现系统缓存、应用更新或用户数据目录混淆。

## 4. 当前代码基线

当前仓库分支为 `main`，协议相关代码主要分布在以下位置：

```text
apps/desktop/src/main/index.ts
apps/desktop/src/renderer/src/pages/login.tsx
apps/desktop/electron-builder.yml
apps/desktop/scripts/package.mjs
apps/desktop/scripts/dev.mjs
packages/core/auth/dingtalk-oauth.ts
apps/web/app/auth/dingtalk/callback/page.tsx
extensions/dingtalk-notify/oauth_login.go
```

当前实现只识别 `desktop` 和 `desktop-dev`，主进程生产环境协议为 `multica`，因此还不能区分定制打包版。

## 5. 总体设计

### 5.1 独立桌面版本模块

新增统一配置模块，例如：

```text
apps/desktop/src/shared/desktop-identity.ts
```

该模块集中定义并导出：

- `variant`：`dev`、`official`、`lechun`；
- `protocol`：`multica-dev`、`multica`、`multica-lechun`；
- `oauthClient`：`desktop-dev`、`desktop`、`desktop-lechun`；
- 应用名称；
- Bundle/App ID；
- 是否启用定制版自动更新。

主进程和渲染进程都从该模块读取配置，避免在多个文件内分别维护字符串。

### 5.2 版本选择方式

建议使用构建时变量选择定制版：

```text
VITE_MULTICA_DESKTOP_VARIANT=lechun
```

开发版不设置该变量时默认使用 `dev`；正式官方打包不设置该变量时默认使用 `official`。

定制版打包脚本负责注入该变量，不要求开发人员手工修改源码或线上 `.env`。

## 6. 具体修改步骤

### 步骤一：新增桌面版本身份模块

新增 `desktop-identity.ts`，提供类型安全的版本映射函数。

要求：

- 未知值回退到官方版或直接让构建失败，不能静默生成错误协议；
- 开发环境仍优先使用 `multica-dev`；
- 定制版必须明确选择 `lechun`；
- 所有映射值集中在一个模块中。

### 步骤二：修改 Electron 主进程协议注册

文件：`apps/desktop/src/main/index.ts`

将现有：

```ts
const PROTOCOL = is.dev ? "multica-dev" : "multica";
```

替换为从桌面身份模块读取的协议。

以下逻辑必须使用同一个 `PROTOCOL`：

- `app.setAsDefaultProtocolClient`；
- macOS `open-url` 事件；
- Windows/Linux `second-instance` 事件；
- 冷启动参数解析；
- `handleDeepLink` 协议过滤；
- 应用名称和 App User Model ID 的设置。

### 步骤三：修改桌面端钉钉登录入口

文件：`apps/desktop/src/renderer/src/pages/login.tsx`

当前登录客户端由开发/生产二选一：

```text
开发版 → desktop-dev
正式版 → desktop
```

改为读取桌面身份模块：

```text
本地开发版 → desktop-dev
定制打包版 → desktop-lechun
官方版 → desktop
```

该客户端标识会写入 OAuth state，必须完整保留到回调阶段。

### 步骤四：扩展共享 OAuth 工具

文件：`packages/core/auth/dingtalk-oauth.ts`

扩展 `DingTalkOAuthClient` 类型和回调映射：

```text
state 以 .desktop-dev 结尾    → multica-dev://
state 以 .desktop-lechun 结尾 → multica-lechun://
state 以 .desktop 结尾        → multica://
```

`isDesktopDingTalkState` 也必须识别 `.desktop-lechun`。

### 步骤五：修改 Web OAuth 回调页

文件：`apps/web/app/auth/dingtalk/callback/page.tsx`

继续使用共享的 `dingtalkCallbackProtocol(state)`，不在页面内单独写协议判断。

授权成功后，定制版跳转为：

```text
multica-lechun://auth/callback?token=<JWT>
```

网页端的 HTTPS 回调地址不变：

```text
https://multica.lechun.cc/auth/dingtalk/callback
```

### 步骤六：扩展服务端 OAuth 客户端白名单

文件：`extensions/dingtalk-notify/oauth_login.go`

新增：

```go
LoginClientDesktopLechun LoginClient = "desktop-lechun"
```

并同步更新：

- `ParseLoginClient`；
- `LoginClientFromState`；
- OAuth state 生成与识别；
- 相关单元测试。

该改动必须部署到线上，否则定制版请求 `client=desktop-lechun` 时会被服务端判定为不支持的客户端。

### 步骤七：新增定制版 electron-builder 配置

保留官方配置：

```text
apps/desktop/electron-builder.yml
```

新增定制版配置：

```text
apps/desktop/electron-builder.lechun.yml
```

定制版配置通过 `extends` 继承官方配置，只覆盖必要差异：

```yaml
extends: electron-builder.yml

appId: ai.multica.desktop.lechun
productName: Multica Lechun

extraMetadata:
  productName: Multica Lechun
  multicaDesktopVariant: lechun

protocols:
  - name: Multica Lechun
    schemes:
      - multica-lechun
```

根据实际发布平台，再为定制版设置独立的产物名称、可执行文件名和 Linux `StartupWMClass`。

### 步骤八：新增定制版打包命令

建议新增：

```bash
pnpm --filter @multica/desktop package:lechun
```

该命令负责：

1. 注入定制版构建变量；
2. 使用 `electron-builder.lechun.yml`；
3. 构建桌面端主进程、预加载脚本和渲染器；
4. 打包对应平台和架构；
5. 输出独立的安装包。

原有命令保持不变：

```bash
pnpm --filter @multica/desktop package
```

本地开发也保持不变：

```bash
pnpm dev:desktop
```

### 步骤九：隔离定制版自动更新

第一阶段建议定制版关闭自动更新，避免定制版从官方更新源下载官方安装包，导致：

- 定制版被覆盖；
- 协议重新变成 `multica://`；
- 定制版与官方版再次冲突。

如果以后需要自动更新，应为定制版配置独立更新频道或独立仓库，并同步修改 `updater.ts` 和发布流程。

## 7. OAuth 完整流程

```text
Multica Lechun 桌面端
        │
        │ /auth/dingtalk/start?client=desktop-lechun
        ▼
钉钉授权页面
        │
        ▼
https://multica.lechun.cc/auth/dingtalk/callback
        │
        │ 校验 state，识别 desktop-lechun
        ▼
multica-lechun://auth/callback?token=<JWT>
        │
        ▼
Multica Lechun 桌面端接收 token 并完成登录
```

## 8. 测试与验收标准

### 8.1 单元测试

- `desktop-lechun` 可以通过服务端客户端标识校验；
- `.desktop-lechun` state 可以被正确识别；
- `.desktop-lechun` 映射到 `multica-lechun`；
- `desktop-dev`、`desktop` 的既有测试继续通过；
- 未知客户端仍然被拒绝。

### 8.2 桌面端测试

- 定制版安装后注册 `multica-lechun://`；
- 定制版不会注册或处理 `multica://`；
- 官方版仍处理 `multica://`；
- 本地开发版仍处理 `multica-dev://`；
- macOS 冷启动、已运行状态、Windows/Linux 第二实例都能接收回调；
- 三个版本可以同时安装并独立启动。

### 8.3 登录链路测试

- Web 端 DingTalk 登录不受影响；
- 本地开发版登录后回到 `multica-dev://`；
- 官方版登录后回到 `multica://`；
- 定制版登录后回到 `multica-lechun://`；
- 回调失败时页面显示明确错误，不进行错误协议跳转。

### 8.4 发布前检查

- 钉钉后台 HTTPS 回调地址已发布且可访问；
- 线上服务端已部署 `desktop-lechun` 支持；
- 安装包的 App ID、产品名、协议和 OAuth client 四项一致；
- 发布包不包含 `.env`、密钥或本地调试配置；
- 定制版更新源不会指向会覆盖它的官方包。

## 9. 对源码更新的影响控制

为了方便未来同步 Multica 上游源码，建议遵循以下边界：

1. 官方 `electron-builder.yml` 尽量不改，只新增 `electron-builder.lechun.yml`；
2. 版本映射集中在独立的 `desktop-identity.ts`；
3. OAuth 扩展只增加新的客户端类型，不改已有 `web`、`desktop`、`desktop-dev` 语义；
4. 打包入口通过新增脚本实现，不重写官方打包流程；
5. 不把定制版逻辑散落到业务页面或通用组件中；
6. 每次同步上游后优先检查协议、OAuth state 和打包配置这三个适配点。

## 10. 上线顺序

建议按以下顺序实施：

1. 先部署服务端 `desktop-lechun` 客户端支持；
2. 再部署 Web 回调和共享 OAuth 工具；
3. 本地运行 OAuth 单元测试和回调测试；
4. 构建定制版桌面安装包；
5. 在未安装官方版、已安装官方版两种环境分别验证协议；
6. 验证成功后再分发定制版安装包。

## 11. 风险与回滚

### 主要风险

- 只修改协议注册但遗漏 OAuth 回调映射，导致授权后无响应；
- 服务端未先部署新客户端标识，导致登录接口返回 unsupported client；
- 定制版仍使用官方 App ID 或自动更新源，导致安装和更新冲突；
- 多个平台配置不一致，导致某一平台协议可用、另一平台不可用。

### 回滚方式

- 定制版问题只回滚定制版配置和脚本，不影响官方版；
- 服务端保留原有三个客户端标识，新增标识可以单独禁用；
- 如果定制版登录异常，可暂时停止分发定制版安装包，官方版和本地开发版继续使用原流程。

## 12. 结论

使用 `multica-lechun://` 作为个人定制桌面版协议是可行的，也是同时安装三个版本时更稳妥的做法。但它不是单点修改：必须同时贯通桌面端协议注册、DingTalk OAuth client、OAuth state、Web 回调映射、服务端白名单和打包 App ID。

推荐采用“独立身份模块 + 独立打包配置 + 增量 OAuth 客户端”的方式实施。这样既能解决当前协议冲突，也能把对 Multica 上游源码的修改控制在少量、明确的适配点内。
